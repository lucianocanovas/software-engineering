Diagrama de Secuencia: Alta, Baja y Modificación (ABM) de Productos
Interacción entre Capas

El siguiente diagrama modela la secuencia de mensajes e interacción temporal entre el Usuario/Navegador, el Controlador MVC, la Capa de Servicios con DTOs, los Mappers, el Repositorio JPA y la base de datos SQLite.

    Note over U,DB: Flujo 1: Alta de Producto (Físico o Digital)
    U->>C: POST /productos/guardar (ProductoDTO con @Valid)
    activate C
    alt Validación fallida (BindingResult hasErrors)
        C-->>U: Retorna vista form con mensajes de error
    else Validación exitosa
        C->>S: guardar(productoDTO)
        activate S
        S->>M: toEntity(dto, categoria)
        activate M
        M-->>S: Entidad ProductoFisico / Digital
        deactivate M
        S->>R: save(productoEntity)
        activate R
        R->>DB: INSERT INTO productos (...)
        DB-->>R: Registro persistido (ID generado)
        R-->>S: Entidad persistida
        deactivate R
        S->>M: toDTO(productoGuardado)
        activate M
        M-->>S: ProductoDTO resultante con precio final calculado
        deactivate M
        S-->>C: ProductoDTO
        deactivate S
        C-->>U: RedirectAttributes (mensajeExito) + Redirección a /productos
    end
    deactivate C

    Note over U,DB: Flujo 2: Consulta y Listado de Productos
    U->>C: GET /productos?filtro=ASUS
    activate C
    C->>S: buscarPorFiltro("ASUS")
    activate S
    S->>R: buscarPorNombreOCodigo("ASUS")
    activate R
    R->>DB: SELECT * FROM productos WHERE activo=1 AND ...
    DB-->>R: Lista de Entidades Producto
    R-->>S: List de Producto
    deactivate R
    S->>M: toDTO() iterativo
    M-->>S: List de ProductoDTO
    S-->>C: List de ProductoDTO
    deactivate S
    C-->>U: Renderiza productos/list.html con Thymeleaf
    deactivate C

    Note over U,DB: Flujo 3: Baja Lógica de Producto
    U->>C: POST /productos/eliminar/{id}
    activate C
    C->>S: darDeBaja(id)
    activate S
    S->>R: findById(id)
    R->>DB: SELECT * FROM productos WHERE id=?
    DB-->>R: Producto
    S->>S: producto.setActivo(false)
    S->>R: save(producto)
    R->>DB: UPDATE productos SET activo=0 WHERE id=?
    S-->>C: void
    deactivate S
    C-->>U: Redirección a /productos con confirmación
    deactivate C

1. Herencia
Usuario → Administrador, Vendedor, EncargadoCompras.
Producto → ProductoFisico, ProductoDigital.
Polimorfismo en cálculo de precio y control de accesos.
2. Agregación
Categoria (1) agrupa a Producto (0..*).
El producto tiene ciclo de vida propio y puede cambiar de categoría sin destruirse.
3. Composición
OrdenDeCompra (1) contiene DetalleOrdenCompra (1..*).
Los renglones no tienen sentido por fuera de la orden; se eliminan en cascada (`CascadeType.ALL`, `orphanRemoval=true`).
4. Asociación
- OrdenDeCompra ↔ Proveedor.
- OrdenDeCompra ↔ EncargadoCompras.
- DetalleOrdenCompra ↔ Producto.
Colaboración estructural entre entidades independientes.
Fundamentos Arquitectónicos: MVC + DTO + ORM SQLite
Patrón MVC con Thymeleaf

Modelo: Representado por entidades JPA (com.techstore.model) y DTOs (com.techstore.dto).

Vista: Plantillas HTML5 con Thymeleaf (src/main/resources/templates/) que procesan expresiones dinámicas del lado del servidor (th:text, th:each, th:field).

Controlador: Clases anotadas con @Controller que reciben las peticiones HTTP, invocan los servicios y despachan las vistas con los modelos asociados.

Uso Mandatorio de DTOs

Desacoplamiento: La vista nunca recibe entidades JPA directamente. Los controladores intercambian exclusivamente DTOs con la capa de servicio.

Seguridad: Previene vulnerabilidades de asignación masiva (Mass Assignment) y protege información sensible como passwords de usuarios.

Validación: Las anotaciones @NotBlank, @Min, @DecimalMin se aplican de forma declarativa sobre los campos del DTO.

Persistencia con SQLite y ORM

Base Embebida: Almacena toda la información relacional en el archivo local techstore.db mediante sqlite-jdbc.

Hibernate Community Dialects: Permite que Spring Data JPA genere sentencias DDL y DML estándar sin requerir un servidor motorizado como MySQL o PostgreSQL.

Lógica de Negocio de Compras & Stock

Cumple exactamente el requerimiento de negocio: "estos se actualizan en el stock de la empresa por medio de compras a sus proveedores mayorista mediante el uso de órdenes de compra que registran el detalle de la misma."

Al confirmar la recepción física, orden.confirmarRecepcion() recorre cada detalle y suma la cantidad adquirida al stock del ProductoFisico referenciado.
